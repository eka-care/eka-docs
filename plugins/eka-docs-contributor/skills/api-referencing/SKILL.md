# API referencing

## The one rule

A request or response schema is written once, in the product's OpenAPI file. Everything else points at it. A `<ParamField>` or `<ResponseField>` on a reference page is a check failure, because it is a second copy that will drift.

## The spec

- One OpenAPI 3.x file per product at `<product>/api-reference/openapi.yaml`. More than one only if the product has independent API surfaces; list each in `product.yaml`.
- Every operation has `operationId`, `summary`, at least one `tags` entry, a request example and a response example for the success case and for each documented error.
- Error codes the product returns appear in the error response examples. The errors page lists the same codes; the check warns on a code it cannot find in any example.
- Webhooks are OpenAPI 3.1 `webhooks` in the same file, keyed by event name (`abha.abha_created`). The webhooks page links each one. Workflow pages name them in `webhooks:` frontmatter.
- Tags group operations the way the reference navigation groups them. Pick tags by what the integrator is doing (Registration, Login, Profile), not by internal service.

## The reference page

```md
---
openapi: "/abdm-connect/api-reference/openapi.yaml POST /abdm/na/v1/registration/aadhaar/init"
---

<Note>The OTP goes to the mobile linked to the Aadhaar, not to the mobile you send.</Note>

{/* used-in:start */}
## Used in
- [Create an ABHA with Aadhaar OTP](/abdm-connect/workflows/create-abha-aadhaar-otp)
{/* used-in:end */}
```

- The `openapi:` value is the **file-prefixed form**: the spec path from the repo root with a leading slash, then `METHOD /path`. The bare form (`POST /path`) makes Mintlify scan every spec in the repo and take the first match by filename, which breaks when two specs share a path. The check accepts bare forms on old pages and warns when one is ambiguous; `/api-sync` rewrites them.
- Notes go under the frontmatter: a gotcha, a rate limit, a sandbox difference. Mintlify renders them with the generated page. Never a schema, never a full example that the spec already carries.
- The "Used in" block is generated by `/api-sync` from workflow pages' `operations`. Do not edit between the markers.

## Converting a hand-written page

Most old pages wrote the schema by hand. To convert one:

1. Read the page. Lift every parameter, body field, response field and example into the spec under the right operation. Preserve descriptions; they are usually the best prose on the page.
2. Replace the page body with `openapi:` frontmatter in the file-prefixed form.
3. Keep anything that was not schema (a warning, a behaviour note) as a `<Note>` under the frontmatter.
4. Run `/api-sync <product>`; it writes the "Used in" block and confirms the operation resolves.
5. Check the rendered page locally with `mint dev` if the CLI is installed; otherwise in the pull request preview.

## The errors page

`type: errors`. Two parts.

**By code.** One table per product, or one per tag if the product is large: code, HTTP status, meaning, what the integrator should do. Codes are the literal strings the API returns (`ABDM-1100`, `MIS-1013`). Each workflow's failure table links here with an anchor.

**By symptom.** A short section per thing the integrator actually sees, because they rarely start from a code: "OTP never arrives", "Every call returns 401", "Callback never arrives", "Request accepted, then nothing". Each: the likely causes in order of frequency, what to check for each, the codes involved if any, and which workflow step it belongs to. Five to eight symptoms is typical; add one whenever support answers the same question twice.

## The webhooks page

`type: webhooks`. For each event: name, when it fires, the payload (link to the spec webhook, do not copy it), delivery and retry behaviour, which workflow consumes it, how to verify the signature if there is one.

## What Mintlify does with the spec

- Generates the request and response panels, the playground, and the code samples from the spec. The page body is rendered above them.
- Picks up `servers` for the playground base URL and `securitySchemes` for auth. Both must be in the spec for Try It to work.
- Uploads every `.yaml` and `.json` in the repo as a spec, whether or not `docs.json` names it. Stale spec files cause ambiguous matches; delete them in the same pull request that stops using them.
